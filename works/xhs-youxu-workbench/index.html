小红书文字工作台

工作环节想法 → 生成 → 选稿修改 → 内容检查 → 导出。
把已有的选题或想法，写成合规可用的小红书文案。

看工作环节 ↓ 内容怎么检查 ↓

22 项自动化测试通过，主流程已用真实模型在本机走通；整体端到端验收仍在收尾。工具只在本机运行，未开放在线试用。

01 / 界面

一次生成，再选一篇改。

先出一套完整稿：标题、正文、话题标签和写作说明。不满意，再出一套不同角度的对比稿，并给出差异导读。选定后继续人工修改或让 AI 定向修改。

02 / 工作环节

从一个想法到可导出的文案。

  1. 01

    想法

    选账号，写选题和想法。账号只需“身份 + 目标读者”，其余自动带入。

  2. 02

    生成

    先出一套完整稿，不满意再出一套不同角度的对比稿。

  3. 03

    选稿修改

    人工修改另存为新版本；也可让 AI 定向改整篇、标题、正文、标签或选中段落。

  4. 04

    内容检查

    模型审核加本地规则。有阻断问题不能放行，提醒级问题可人工放行。

  5. 05

    导出

    只有通过检查的当前版本，才能复制或下载为 Markdown / TXT。

工具不自动发布，也不保证平台审核通过；发布记录由人手动登记。

03 / 内容检查

不编造，改了就重新检查。

教育类内容最怕两件事：写出没发生过的经历和效果，以及踩平台规则。工具把这两件事放进了流程，而不是靠写完再人工盯。

内容真实性约束

模型被要求“没给真实经历就不写亲测、我家上过”。产品事实只来自用户提供的资料，不得编造价格、效果和渠道。本地确定性规则再兜底，拦截禁用表达和违规引导。

版本与检查绑定

每次修改都保留旧版本，可回看差异。检查结果绑定具体版本；任何输入或修改都会让旧的“已通过”失效，必须重新检查才能导出。

检查意见要能对上原文

模型给出的检查意见会引用原句，工具核对这句话是否真的在稿件里。对不上原文的，降级为“请人工核对”，不作为阻断依据，避免模型编造的问题拦住好稿子。

失败可恢复

每次模型调用保留输入快照、用量、耗时和请求 ID。超过 300 秒或失败时保留旧稿，可一键重试。API Key 只存在服务器配置文件里，不经过浏览器。

04 / 实现与边界

当前做到哪里。

需求、流程和检查规则由我设计并验收，开发由 AI 辅助完成。

已验证＋

22 项自动化测试通过，覆盖存储、模型连接、主链路状态流转、改动使检查失效、提醒级问题人工放行、阻断问题不可放行等关键路径。

完整生成流程已在本机真实库上走通；重复稿拦截、300 秒超时、同一选题重复提交被拒、窄屏弹窗布局等已实测。

还没做完＋

整体端到端验收仍在收尾，部分浏览器内场景尚未逐项验证。本页不把它写成已全部验收。

没有公开的在线试用入口，也没有可证明的效率或涨粉数据。

实现方式与使用边界＋

Node.js 24.5 以上，只用标准库和内置 SQLite，没有 npm 依赖和构建步骤；前端是原生 HTML、CSS 和 JavaScript。这是个人本地工具，目标是能跑、好改、可解释。

只监听本机地址，不适合直接开放到公网；不接小红书平台接口，不自动发布，不抓评论私信，不读平台数据。内容质量最终仍需人工把关，模型检查是辅助。
